ESP8266 联网功能开发计划

USART3 (PB10/PB11) + ESP8266 AT 固件 · 制定于 2026-09-23 · 基于 N0 前可查证的全部工程事实
结论先行
  • 路线已定：ESP8266 保持 AT 固件，STM32 侧自写轻量 AT 引擎（~700 行，FreeRTOS 原生），一期 TCP 透传上报环境数据，二期按固件能力决定是否直接上 MQTT AT。
  • 不引入 LwIP：P2 刚把 LwIP+ETH 拔掉省出 64KB RAM，ESP8266 走 AT 天然不需要协议栈——这条路和当年决策自洽。
  • 不搬源工程代码：AIR724 的 at_device 是 RT-Thread 框架组件（2360 行，深度耦合 at_client/netdev），只借鉴其"设备控制操作集 + URC 表 + 状态机"设计，代码重写。
  • 硬件白送：ioc 里 USART3 已配好异步+上拉，MX_USART3_UART_Init() 已在生成序列——P1 直接从驱动层开始，不碰 CubeMX 图形界面。
  • 总盘子 6 天（N0~N5），3 个人工审核点，每阶段有明确验收门。

① 方案选型（为什么不走别的路）

方案说明结论
A. AT 固件 + 自写 AT 引擎ESP8266 官方/安信可 AT 固件，STM32 串口发 AT 指令，自写轻量解析器✅ 采用零 ESP 侧开发、RAM 占用最小、协议可控
B. 移植 RT-Thread at_client源工程 AIR724 同款框架❌ 否决深度耦合 RTOS，移植成本 > 重写，且引入大堆依赖
C. LwIP + ESP8266 PPPSTM32 跑完整协议栈，ESP 只当调制解调器❌ 否决复杂度爆炸，还把刚省出来的 64KB RAM 吃回去
D. ESP8266 刷 NodeMCU/自写固件双端开发，自定义串口协议暂缓多一块开发调试工作量；除非 AT 固件版本烂到没法用才回头考虑

② 数据流架构（怎么嵌进现有骨架）

USART3 中断收 ──▶ 环形缓冲 ──▶ 行分帧 ──▶ AT 引擎解析 │ ┌─────────────────────────┤ ▼ ▼ [espTask 新增] URC: +IPD / WIFI DISCONNECT 1s 周期状态机 │ ├─ 读 smart_data 快照 ▼ ├─ 序列化(0.1定点→文本) ──▶ CIPSEND 上报 └─ 写 g_net_status ──▶ smart_data ──▶ UI WiFi 图标 （单写多读原则不破坏：net 字段唯一生产者是 espTask）

关键约束：UI 永不直接等网络；网络下行命令（二期）经命令队列转交 smartPeriodic 应用，不抢 smart_data 单写者地位。

③ 阶段计划 N0–N5

N0 硬件体检 0.5 天 · 人工审核点 1

目标：摸清模组底细，锁死二期 MQTT 走法
#事项验收
1核对接线：PB10(TX)→ESP8266 RX，PB11(RX)→ESP8266 TX，共地，独立 3.3V 供电万用表确认 3.3V ≥ 3.0V 且不跌落
2USART1 调试口透传 AT（临时桥接脚本），发 AT+GMR / AT+CWMODE?拿到固件版本号 + 模式能力清单
3决策：固件 ≥ esp-at v2.2 → 二期直接 AT+MQTT*；否则二期 TCP 收尾本计划 ④ 节勾选最终走法
审核门：版本/供电结论同步同学，确认 WiFi 热点 SSID/密码与云端形态（TCP 直连 or MQTT broker）。

N1 串口驱动层 1 天

新文件：bsp/components/esp8266/esp8266_uart.c/.h（约 200 行）
#事项要点
1USART3 中断收（HAL_UART_Receive_IT 单字节 + 环形缓冲 1KB）115200 下 11.5k 中断/s ≈ CPU 1~2%，168MHz 无压力；故意不用 DMA——不必改 ioc，避开 CubeMX 重生成回退风险
2行分帧器：\r\n 结尾成行，最长 512B 溢出保护AT 响应 + URC 全按行处理
3阻塞发送 + 发送互斥（AT 命令是半双工问答）FreeRTOS mutex
4测试桩：上电发 AT → 收 OK，[esp] 前缀打日志CMakeLists 加 target_sources + include（显式列表，别忘）
验收门：串口见 [esp] AT -> OK 往返 100 次零错位。

N2 AT 引擎 1.5 天

新文件：bsp/components/esp8266/esp8266_at.c/.h（约 500 行）+ app/smart/smart_net_task.c/.h
#事项要点
1命令-响应引擎：at_cmd(req, expect[], timeout) 带超时重试 ×2借鉴源工程 at_device 的命令表思想，返回码统一 ESP_OK/ESP_ERR/ESP_TIMEOUT
2URC 分发表：+IPD（下行数据）/ WIFI DISCONNECT / busy p...URC 异步到达，引擎收完响应后扫描残留行
3espTask（4KB 栈起步，osPriorityNormal）：开机自检 → WiFi 状态机（init→connecting→online→reconnect）栈水位靠 [mon] 实测后裁剪（×2 峰值法，历史铁律）；IWDG 由 defaultTask 喂，espTask 无狗压力
4freertos.c 创建任务 + smart_data.h 增加 g_net_status（0 离线/1 连接中/2 在线）monitor_task 的 stk 行自动覆盖新任务
验收门：上电自动连 WiFi，[esp] WIFI CONNECTED, ip=x.x.x.x；拔路由器 30s 内自动重连。

N3 WiFi + TCP 透传 1 天

打通端到端：smart_data → 云端可见
#事项要点
1连接序列：CWMODE=1 → CWJAP → CIPSTART → CIPMODE=1 → CIPSEND透传退出坑：+++ 前后各 1s 静默，封装成 esp_exit_transparent()
2上报帧：1s 周期打包 temp[3]/humi/co2/pa/tar_temp（0.1 定点整数，JSON 单行）变化检测：值没变不发，省流量（沿 UI 刷新同款模式）
3PC 端验证服务：python -m serial.tools 同款思路写 20 行 TCP 收包脚本tools/ 下 net_recv.py，验收时可复用
审核门 2：PC 收到实时环境数据 JSON；掉线→重连→续报全程无人工干预。

N4 应用集成 1.5 天

让联网"看得见"

⚠ 红线（每条都踩过或高发）

供电是 ESP8266 第一大坑ESP-01S 峰值 300mA+，探索者板载 3.3V 直接带会电压跌落→模组莫名复位掉线。独立 LDO 或 ≥470µF 电容就近储能。
新增文件必须当天进 CMakeLists + commit显式文件列表忘了加=编译报 undefined；改动挂着不提交=上次 lcd.c 事故重演。
[esp] 日志与 [mon]/[ui] 并发USART1 是共享受限资源，esp 日志走同一 dbg_printf，注意别在 ISR 里打。
栈顶穿 = IWDG 循环复位新任务上线第一时间看 [mon] stk 行，espTask 峰值 ×2 不足 4KB 立即调。
